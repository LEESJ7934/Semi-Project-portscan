# Project Story — 이력서·포트폴리오·면접 정리

이 문서는 저장소 기능 설명이 아니라
**왜 프로젝트를 이렇게 개선했는지 설명하기 위한 인터뷰 노트**다.

## 1. 한 줄 소개

> 단순 포트 스캔 프로젝트를 승인 자산 관리, 서비스·버전 식별,
> 검토된 CVE 후보, 읽기 전용 검증, 위험 우선순위, 증적·조치이력,
> JSON/PDF 보고서까지 연결되는 인프라 보안진단 파이프라인으로 개선했습니다.

## 2. 처음 문제

초기 세미프로젝트의 핵심은 포트 스캔이었다.

```text
대상 입력
  |
  v
포트 스캔
  |
  v
열림 / 닫힘 결과
```

하지만 실제 보안 관리 관점에서는 열린 포트를 발견하는 것만으로
다음 질문에 답하기 어려웠다.

- 이 대상은 스캔해도 되는 자산인가?
- 누가 관리하는 자산인가?
- 같은 자산을 다시 발견했을 때 어떻게 추적할 것인가?
- 80번 포트가 정말 어떤 제품·버전인가?
- 버전이 취약 범위라고 해서 실제 취약하다고 말할 수 있는가?
- 여러 finding 중 무엇부터 볼 것인가?
- 검증 결과와 상태 변경 근거를 어떻게 남길 것인가?
- 나중에 결과를 다시 설명할 수 있는가?

그래서 프로젝트 목표를
**포트 탐지 기능 추가**가 아니라
**관찰 → 판단 → 검증 → 우선순위 → 증적**의 흐름을 만드는 것으로 바꿨다.

## 3. 개선 흐름

### 단계 1 — 자산과 승인 범위

먼저 스캔 기능보다 실행 경계를 강화했다.

추가한 내용:

- IP/CIDR/호스트 입력
- 승인 scope와 유효기간
- 최대 대상·포트·동시 작업 수
- 자산 UUID
- 중요도, 담당자, 환경, 데이터 등급
- 개인정보 처리 여부
- 인터넷 노출 여부
- 자산 변경 감사이력
- 스캔별 관찰 이력

핵심 판단:

> 보안 스캐너는 많이 스캔하는 것보다
> 허가받은 대상을 통제 가능하게 스캔하는 것이 먼저라고 봤습니다.

### 단계 2 — 서비스·버전 식별

포트 번호를 서비스 결과처럼 사용하지 않도록 바꿨다.

```text
port 8080
```

만 저장하는 대신 응답을 관찰해:

```text
service = http
product = apache_http_server
version = 2.4.50
source = http_server
```

처럼 근거와 함께 저장했다.

식별 실패 시 과거 제품·버전을 그대로 재사용하지 않았다.

### 단계 3 — CVE 후보

서비스/버전과 CVE를 연결할 때 전체 인터넷 CVE를 무작정 매칭하지 않았다.

공식 공지를 직접 검토한 4개 CVE만 작은 규칙집으로 만들고:

- 제품 일치
- 숫자 버전 범위
- 출처
- 적용 조건
- 규칙 hash

를 저장했다.

결과는 `CONFIRMED`가 아니라 `CANDIDATE`다.

### 단계 4 — 읽기 전용 검증

후보를 실제 검토 상태로 진행시키기 위해 CVE별 verifier를 분리했다.

안전 원칙:

- 승인 scope 재확인
- 인증 시도 금지
- 업로드/삭제 금지
- 공격 payload 금지
- 읽기 전용 observation
- timeout/연결 실패는 ERROR
- 단순 HTTP 200은 CONFIRMED 근거가 아님

검증 결과를 evidence와 remediation history에 함께 남겼다.

### 단계 5 — 우선순위

취약 여부와 대응 우선순위를 분리했다.

입력:

```text
CVSS
EPSS
CISA KEV
자산 중요도
인터넷 노출
개인정보 처리 여부
현재 finding 상태
```

출력:

```text
action
priority P1~P4 / UNASSESSED
matched rules
reason
missing inputs
methodology hash
```

외부 API 오류를 0점으로 바꾸지 않는 것이 중요한 설계 결정이었다.

### 단계 6 — 보고서

마지막에는 지금까지 저장한 데이터를 하나의 snapshot으로 읽어
JSON/PDF 보고서를 생성하도록 했다.

보고서 생성이:

- 스캔을 다시 하지 않고
- 외부 API를 다시 부르지 않고
- DB를 수정하지 않고

같은 snapshot을 그대로 표현하게 했다.

## 4. 가장 설명 가치가 큰 설계 판단

### Q1. 왜 서비스 버전만 보고 취약점을 확정하지 않았나요?

배너는 서버가 주장하는 문자열일 뿐이고,
배포판 backport나 설정 조건을 알 수 없기 때문이다.

그래서:

```text
fingerprint
→ CANDIDATE
→ read-only verification
→ analyst review
```

단계로 나눴다.

### Q2. 왜 오류를 false positive와 분리했나요?

timeout은 "취약하지 않음"이라는 증거가 아니다.

```text
timeout → ERROR
정상 관찰 + 조건 불일치 → 검토 결과
```

로 의미를 분리해야 잘못된 안전 판정을 피할 수 있다.

### Q3. 왜 외부 점수 오류를 0으로 저장하지 않았나요?

0은 실제 관찰값처럼 해석될 수 있다.
조회 실패는 `NULL`, `UNKNOWN`, `incomplete`로 표현해서
데이터 없음과 낮은 위험을 구분했다.

### Q4. 왜 우선순위를 취약점 상태와 분리했나요?

`POTENTIAL`이라도 KEV에 올라 있고 중요 자산이면 빨리 검토해야 할 수 있다.
반대로 priority가 높다고 기술적으로 취약점이 확정되는 것도 아니다.

그래서 vulnerability state와 triage priority를 별도 축으로 관리했다.

### Q5. 왜 보고서에서 API를 다시 호출하지 않았나요?

보고서 생성 시점마다 외부 값이 바뀌면
DB에 저장된 판단 근거와 보고서가 달라질 수 있다.

따라서 보고서는 저장된 snapshot의 표현 계층으로 제한했다.

## 5. 실제 문제 해결 사례

### 사례 1 — 포트 범위 저장 길이

기본 범위처럼 포트가 많을 때
파싱된 전체 목록을 그대로 문자열화하면 기존 DB 컬럼 길이를 초과할 수 있었다.

해결:

- 포트를 정렬·중복 제거
- 연속 범위를 `1-1024`처럼 압축
- DB 컬럼을 MEDIUMTEXT로 확장
- 원래 입력은 config snapshot에 별도 보존

배운 점:

> 입력 표현과 실제 실행 결과 표현은 목적이 다르므로 분리해야 했습니다.

### 사례 2 — 배너 기반 과도한 확정

Apache 2.4.50 문자열을 관찰했다고
실제 CVE가 재현됐다고 말할 수 없었다.

해결:

- `CANDIDATE`
- CVE별 verifier
- `POTENTIAL`
- 추가 확인 조건

으로 단계화했다.

배운 점:

> 자동화는 판단을 빠르게 할 수 있지만,
> 근거가 부족한 상태를 확정 상태로 올리면 안 됩니다.

### 사례 3 — 반복 실행 중복

같은 finding, evidence, risk 평가를 여러 번 실행하면
DB가 중복 row로 늘어날 수 있었다.

해결:

- UNIQUE 기준
- evidence hash
- canonical assessment input hash
- observations / last_assessed_at 갱신

을 사용했다.

배운 점:

> 운영 도구는 한 번 실행됐을 때보다 반복 실행됐을 때의 동작이 더 중요했습니다.

## 6. 이력서용 4줄

아래는 과장하지 않는 범위의 예시다.

> **서비스 포트 스캐너 기반 인프라 보안진단 프로젝트 개선**
> - 승인 스코프·유효기간·실행 한도를 적용하고 자산 중요도/담당자/개인정보 처리 여부 및 변경이력을 관리하는 자산관리 구조 구현
> - TCP 서비스 응답 기반 제품·버전 fingerprint와 공식 공지 영향 범위를 비교해 CVE 후보 및 선정 근거를 저장하는 분석 파이프라인 구현
> - CVE별 읽기 전용 검증, 증적·상태이력, NVD CVSS/FIRST EPSS/CISA KEV와 자산 맥락 기반 설명 가능한 우선순위 평가 구조 구현
> - MySQL V5 결과를 consistent read snapshot으로 조회해 assessment freshness·증적·조치이력을 포함한 JSON/PDF 보고서 생성 및 회귀/E2E 검증

## 7. 노션 포트폴리오용 설명

### 프로젝트 목적

기존 포트 스캔 프로젝트는 열린 포트와 일부 분석 결과를 확인할 수 있었지만,
실제 보안 관리에서 필요한 승인 범위, 자산 맥락, 취약점 판단 근거,
검증 상태, 반복 관찰 이력까지 연결되어 있지 않았습니다.

그래서 단순 스캔 기능을 늘리기보다
**승인 자산을 기준으로 관찰 결과가 취약점 검토와 대응 우선순위까지 이어지는 흐름**을 설계했습니다.

### 주요 개선

1. **승인 기반 스캔**
   - IP/CIDR/호스트 대상
   - scope 유효기간
   - 최대 대상·포트·worker 제한
   - dry-run

2. **자산관리**
   - UUID 기반 자산
   - 중요도/담당자/환경/데이터 분류
   - 개인정보 처리·인터넷 노출 여부
   - 변경 전후 감사이력

3. **서비스·CVE 분석**
   - 실제 응답 기반 service/product/version
   - 검토된 공식 영향 범위
   - 후보 이유·출처·규칙 hash

4. **보수적 검증**
   - 읽기 전용 CVE verifier
   - 오류와 false positive 구분
   - evidence 및 remediation history

5. **위험 우선순위**
   - CVSS/EPSS/KEV
   - 자산 중요도/노출/개인정보
   - 설명 가능한 rule과 methodology hash

6. **보고서**
   - current-state snapshot
   - assessment CURRENT/STALE/MISSING
   - JSON/PDF 동일 snapshot
   - 증적·조치이력 포함

### 결과

단순히 "어떤 포트가 열렸는가"에서 끝나는 프로젝트를
"왜 점검 대상인지, 어떤 서비스가 관찰됐는지, 왜 CVE 후보인지,
무엇을 추가 검증해야 하는지, 무엇부터 대응해야 하는지"를
근거와 이력으로 설명할 수 있는 구조로 개선했습니다.

## 8. 60초 면접 답변

> 처음에는 TCP/UDP 포트를 스캔하고 결과를 저장하는 세미프로젝트였습니다.
> 그런데 실제 보안 관리 관점에서는 열린 포트를 찾는 것만으로는
> 승인된 자산인지, 어떤 제품과 버전인지, 실제 취약 가능성이 있는지,
> 무엇부터 대응해야 하는지를 설명하기 어렵다고 판단했습니다.
>
> 그래서 먼저 승인 스코프와 자산관리 구조를 추가하고,
> 실제 서비스 응답에서 제품·버전을 식별하도록 개선했습니다.
> 이후 공식 공지의 영향 범위를 검토한 작은 CVE 규칙집으로 후보를 만들되
> 배너만으로 취약점을 확정하지 않고 CVE별 읽기 전용 검증 단계와
> 증적·상태이력을 분리했습니다.
>
> 마지막으로 NVD CVSS, FIRST EPSS, CISA KEV와 자산 중요도·노출 여부를 조합한
> 설명 가능한 우선순위를 저장하고, 동일 DB snapshot에서 JSON/PDF 보고서를
> 생성하도록 연결했습니다. 개선 과정에서는 반복 실행 중복, 네트워크 오류 오판,
> 외부 API 실패를 0점으로 처리하는 문제 같은 경계 조건도 테스트했습니다.

## 9. 예상 꼬리질문

### "왜 Nmap을 그냥 쓰지 않았나요?"

Nmap을 대체하는 것이 목표가 아니었다.
포트 스캔 이후 자산·취약점 후보·검증·이력·우선순위·보고서를
하나의 데이터 흐름으로 직접 설계하고 이해하는 것이 목표였다.

상용/전문 스캐너와 경쟁한다고 설명하면 안 된다.

### "왜 CVE가 4개뿐인가요?"

전체 CVE 자동 매칭을 가장하지 않기 위해서다.
제품명과 버전만으로 신뢰할 수 있는 영향 범위를 표현하려면
공식 공지를 검토하고 제품별 버전 규칙을 만들어야 했다.

그래서 작은 검증 가능한 rule set으로 시작하고
미일치를 안전 판정으로 해석하지 않았다.

### "CVE-2021-42013을 검증했는데 왜 CONFIRMED가 아니죠?"

원격 HEAD와 배너만으로 실제 취약 설정,
설치 패키지, 배포판 backport 여부를 확정할 수 없기 때문이다.

따라서 `POTENTIAL`과 추가 확인 조건을 남기는 것이 더 정확하다.

### "P2면 취약하다는 뜻인가요?"

아니다.
P2는 프로젝트의 대응 우선순위이고 vulnerability verdict가 아니다.
예를 들어 KEV와 높은 CVSS 때문에 빨리 검토해야 할 수 있지만
기술 상태는 여전히 POTENTIAL일 수 있다.

### "왜 risk score 하나로 계산하지 않았나요?"

숫자 하나만 남기면 왜 우선순위가 높아졌는지 설명하기 어렵다.
그래서 P1~P4 rule과 matched rule, reason, missing input을 저장했다.

### "왜 과거 스캔을 완전히 재현하지 못하나요?"

현재 `ports`는 최신 관찰 상태 중심이다.
스캔 ID와 증적은 남지만 모든 포트 snapshot을 실행별로 완전히 보존하는
event-sourcing 구조는 이번 범위에 포함하지 않았다.

이 한계를 숨기지 않고 보고서 selection note에 명시했다.

### "DVWA와 Nuclei는 어디에 쓰나요?"

로컬 승인 실습환경에서 웹 검증, 도구 연동, screenshot/evidence를 연습하는 용도다.
현재 Day 5 상태 전이의 핵심은 CVE별 읽기 전용 verifier이며,
Nuclei 결과 하나로 자동 CONFIRMED하지 않는다.

## 10. 표현 주의

이 프로젝트를 다음처럼 과장하지 않는다.

- "상용 ASM 구축"
- "전체 CVE 자동 탐지"
- "Nmap 대체"
- "취약점 자동 확정 엔진"
- "실제 기업망 공격 검증"
- "CVE 미탐지 = 안전"
- "P1/P2 = 취약점 확정"

대신 다음처럼 설명한다.

- "교육용/포트폴리오용 인프라 보안진단 파이프라인"
- "승인 scope 기반 포트 스캔과 자산관리"
- "검토된 소규모 CVE 규칙집"
- "읽기 전용 검증과 상태·증적 이력"
- "외부 위협정보와 자산 맥락을 결합한 프로젝트 triage policy"
- "현재 상태 snapshot 기반 보고서"

## 11. 면접 전에 반드시 직접 설명할 수 있어야 하는 것

```text
[ ] scope가 왜 필요한가
[ ] port hint와 fingerprint의 차이
[ ] CANDIDATE와 CONFIRMED 차이
[ ] timeout이 왜 ERROR인가
[ ] evidence 중복을 어떻게 막았는가
[ ] remediation_history가 왜 필요한가
[ ] CVSS/EPSS/KEV 역할 차이
[ ] P1~P4가 vulnerability verdict가 아닌 이유
[ ] input_sha256을 왜 저장하는가
[ ] CURRENT/STALE/MISSING의 의미
[ ] report가 외부 API를 다시 부르지 않는 이유
[ ] 프로젝트가 하지 않는 것
```

이 질문들에 코드 전체를 외우지 않고도
`문제 → 판단 → 구현 → 검증 → 한계` 순서로 답할 수 있으면 된다.
